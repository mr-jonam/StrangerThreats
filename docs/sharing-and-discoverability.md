# Share and discover StrangerThreats

This page keeps the repository easy to find without turning the README into a
keyword dump. The repository content is prepared below; the **About** metadata
and social preview must be configured by an administrator in GitHub's web UI.

## Configure GitHub metadata

Open the repository home page, select the gear beside **About**, and use:

- **Description:** `Cybersecurity knowledge base for threat analysis, incident response, defensive security, reporting, tools, and career paths.`
- **Website:** leave empty until there is a maintained project website. Do not
  point it to an unrelated profile or short-lived page.
- **Topics:**

  ```text
  cybersecurity
  infosec
  threat-intelligence
  threat-analysis
  threat-modeling
  incident-response
  digital-forensics
  blue-team
  defensive-security
  security-operations
  soc
  application-security
  appsec
  cloud-security
  vulnerability-management
  mitre-attack
  owasp
  nist
  cyber-threat-intelligence
  cybersecurity-resources
  ```

GitHub permits up to 20 public topics. Use lowercase letters, numbers, and
hyphens only. Retain only topics that accurately describe material actually in
the repository; relevance is more useful than maximum count.

For the social preview, upload a consistent PNG/JPG/GIF with a solid background,
project name, and a short subtitle such as `Defensive cybersecurity knowledge
base`. GitHub recommends 1280 × 640 pixels and a file below 1 MB. Do not place
secrets, client logos, unlicensed imagery, or vulnerable-system screenshots in
the image.

## Make participation easy

1. Enable **Discussions** in `Settings → Features → Discussions` and publish a
   pinned welcome post pointing newcomers to the learning paths, reporting
   template, and contribution guide.
2. Pin this repository on the `mr-jonam` GitHub profile and keep the first README
   screen focused on the value and the main paths.
3. Turn useful questions into improvements: link a source, add a dated note, or
   submit a sanitized report. Use issues for concrete repository work and
   Discussions for questions and ideas.
4. Publish small, dated updates rather than repeatedly reposting the whole
   repository. Examples: a new incident-response checklist, a reviewed tool
   entry, or a refreshed threat-landscape source.

## Sharing plan

Share the repository only where the audience benefits from defensive, legal, and
source-backed material. Read each community's current rules first, explain the
specific resource you are offering, and avoid unsolicited direct messages or
engagement bait.

| Channel | Best use | Suggested first post |
| --- | --- | --- |
| GitHub | Source of truth | Enable Discussions and pin a welcome post. |
| LinkedIn | Practitioners and hiring-oriented learners | Share one learning path or template, its intended user, and the repository link. |
| Mastodon / Bluesky / X | Short updates and peer discovery | Post a single new resource, source, or release note; use a descriptive link preview. |
| OWASP chapters and local security meetups | Community learning | Ask organizers before sharing; offer a short walkthrough or contribution session. |
| Reddit or specialist forums | Targeted feedback | Post only when rules allow self-promotion; lead with a question or useful excerpt, not a request for stars. |
| Curated “awesome” lists | Long-term discovery | Open a focused pull request only when the repository matches the list's inclusion rules. |

## Measure usefulness, not vanity metrics

Review monthly: unique contributors, accepted improvements, recurring discussion
questions, external references, and which learning paths people actually use.
Archive or clarify stale links, record review dates for volatile claims, and let
community feedback guide the next guide or template.
